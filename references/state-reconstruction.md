# 共享状态重建规则

status、checkpoint、compress、handoff、restore、verify（含 health-check 别名）的唯一公共事实判断层。各模式控制读取顺序、写入范围和输出形式；本文件统一事实判断，不授权额外修改。

## 1. 项目范围

- 优先使用用户指定项目，其次使用当前已明确的项目上下文与工作目录。用目录入口、项目清单和 Git 根目录交叉确认；Git 根目录不一定等于当前子项目范围。
- 记录仓库/项目、当前工作树及子项目（如适用）。单仓多模块只扩展到当前任务所需的共享依赖；跨仓任务分别维护基线，再描述关联。
- 存在多个同样合理的候选且无法确定时，先询问项目路径；不要猜测“之前的项目”，不要扫描用户所有项目寻找记忆。
- 读取项目根目录 AGENTS.md（若存在）及当前范围适用的嵌套指令，检查 AGENTS.override.md 等有效覆盖；了解原文不代表忽略更高优先级或覆盖规则。
- 非 Git 项目继续依据文件与验证结果工作，Git 字段写“不适用”；工具不可用、权限不足和仓库尚无提交分别说明，不混写成“不适用”。

## 2. 文档与代码发现

先做有限文件名/目录检索，优先使用 rg --files 和 rg；再读 README、项目清单、配置、构建入口及文档索引。避开依赖目录、构建产物、大型数据和无关日志，不绕过忽略规则来扩大扫描。

按内容识别概述、架构、进度、ADR/决策、TODO/backlog、Issues、roadmap 、Handoff 和 Checkpoint/current-work，建立“用途 → 现有路径”的映射。同一文档可以承担多个用途；不要求固定文件名或七份独立文档。链接到不可访问的外部资料时记录缺口，不推断其内容或自动修改外部系统。

文档提供定位线索；根据当前任务、入口调用链、配置和近期相关差异阅读关键代码与测试。检查必要的注册、接线和调用方，区分可用路径、孤立实现、占位及仅有设计。停止条件是：当前任务的关键结论已有可追溯证据，或剩余缺口已明确；不追求读完整个仓库。

使用仓库相对路径和稳定符号定位证据；行号可辅助，但不能作为唯一依据。不能因为一处搜索没有结果，就断言整个功能不存在。

## 3. 证据优先级与状态分类

判断当前实现事实时采用：**当前代码 > Git > 项目文档 > 当前任务记录 > 聊天记录**。先确认这些来源指向同一范围和版本。代码说明实际实现，Git 说明变更与版本；提交说明、文件名和聊天结论都不能替代实现检查。

该顺序不改变用户目标、授权或规范的效力。当前代码可以违背有效约束，不能因此修改约束来宣告代码正确。区分“实际架构”“目标架构”和“已接受决策”。

| 实现状态 | 使用条件 |
|---|---|
| 已实现且已验证 | 相关实现和必要接线存在，针对所声称行为的验证在记录的基线上通过；注明验证范围 |
| 已实现，验证未确认 | 实现证据存在，但当前行为尚无适用的成功验证；具体区分未运行、失败、受阻或未完成，已有失败不可简写为未验证 |
| 部分实现 | 已确认存在实现，但仍有具体行为、接线或验收缺口 |
| 仅设计 / 待实现 | 只有方案，或在足够明确的检查范围内确认尚无所需实现 |
| 不确定 | 证据不足、来源冲突或检查范围不足以分类 |

Completed 只能放已确认存在的成果，并保留其验证限定；不能把“未验证”隐藏在总体“完成”表述下。测试通过只支持所覆盖行为，不等同于全项目完成、已经部署或生产可用。

目标和决策理由无法从代码确定时，引用明确需求、ADR 或可访问的讨论。仅有推测则标为“推断”，理由缺失则写“原因未记录”。

## 4. Git 与核验基线

在已确认目录中使用只读检查，例如：

```text
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short --branch
git log -n 10 --oneline
git diff --stat
git diff --cached --stat
```

再针对相关路径查看暂存/未暂存 diff 和重要提交；相关未跟踪文件须实际读取才能判断。记录 detached HEAD、无提交、冲突合并或工具错误；不运行 Git 状态变更命令，不为收集历史而自动 fetch。

Handoff / Checkpoint 的 Evidence Scope / Verification Baseline 至少记录（可在现有字段中承载或引用，勿重复抄写）：

| 字段 | 含义 |
|---|---|
| Repository / Project Scope | 可辨识项目标识、范围边界；不使用带凭据的远程 URL |
| Subproject | 当前模块/服务，或不适用 |
| Branch | 检查时分支或 detached HEAD 等实际状态 |
| HEAD | 检查时提交标识，或无提交/不适用/无法读取及原因 |
| Working Tree | 检查时干净/有修改/有冲突；区分暂存、未暂存、相关未跟踪文件并概括相关变化 |
| Relevant Files Inspected | 实际读过的关键文件/符号及支持的结论，不能列尚未读取的文件充数 |
| Validation Run | 实际命令、执行目录、状态、时间、范围和重要失败摘要；引用验证表可避免重复 |
| Last Verified | 实际核验时间及明确时区；不是仅生成文档的时间 |
| Evidence Gaps | 未检查内容、缺失来源、未验证假设和冲突；没有已知缺口也需限定检查范围 |

比较 Handoff / Checkpoint 与当前范围、分支、HEAD 以及相关工作区变化。HEAD 改变只表示需要检查差异，不直接证明所有内容失效；HEAD 相同仍可能存在影响行为的未提交变化。若旧基线只有“dirty”而无足够细节，重新读取当前任务关键文件，不能声称未提交内容未变。

Handoff / Checkpoint 日期较旧是检查线索，不能单独决定过期；判断变化是否影响当前任务。已核验的结论可沿用，未核验旧结论须注明来源及状态。资料来自另一工作树时重新确认本地文件是否包含交接中的修改。

文档写入造成的 working tree 变化与实现变化分开描述：基线标明在上下文文档写入前采集，结束时报告本次写入的文档。不要为了把 Handoff 自身加入 dirty 清单而循环改写基线。

## 5. 验证状态

从适用 AGENTS.md、项目脚本、配置和 CI 中确定已有命令，不凭框架名称猜命令。执行前检查命令内容及影响，选择能确认当前关键事实的最小合理检查。

| 状态 | 定义 |
|---|---|
| Passed | 命令实际执行成功，注明所覆盖行为、目录和代码/工作区基线 |
| Failed | 已执行并失败；保留命令、退出状态（可取得时）、失败摘要和影响 |
| Not run | 未执行，注明成本、缺少明确方式或不属于本次需要等原因 |
| Blocked | 环境、权限、依赖或服务阻碍执行/完成，不能据此断言产品代码失败 |
| Incomplete | 超时、中断或仍在运行，不能当作成功 |

只读代码检查应写“静态检查”，不伪装成已运行测试。旧测试结果注明旧时间与基线，不自动提升为当前通过。

运行成本合理、范围明确、无破坏性副作用的现有验证。格式化写入、自动修复、安装依赖、迁移数据库、调用付费服务或写入外部系统不属于默认验证；可选择现有只检查模式，或记录未执行原因。不要为上下文整理修复失败测试或大范围修改代码。

status/restore/verify（含 health-check）的只读范围也适用于验证副作用。会写项目文件的命令，只有能安全使用项目现有的只检查方式或将产物定向到允许的临时位置时才运行；否则记录 Not run。不能因为命令名含 test 或 build 就忽略它的写入行为。

## 6. 冲突与不确定性

每个影响后续工作的冲突简记“主张 / 当前证据 / 判断 / 待处理动作”。

- 聊天或任务说完成，代码缺失或只部分实现：按实际证据分类，记录验收缺口。
- 进度/TODO 落后，相关实现与验收证据充分：标识可同步项；是否写入由模式控制。
- 架构文档描述过去实现：区分现状说明与规范，只有明确的现状说明可按证据同步。
- 代码违反 ADR/约束：记录实现偏差，不改写 ADR 使其合法化。新实现不等于已批准的新决策。
- 多份文档冲突：确定各自范围和版本；保留仍有效历史，无法判断时明确未决，不以文件较新作为唯一理由。
- 明确的新决策替代旧决策：只在有决策依据时记录替代关系、理由、影响和重审条件；不删除旧决策来缩短文档。

对重要结论标记事实、推断或不确定，并给出证据位置/缺口和最小核实动作。推断和不确定事项不得混入已确认成果。只有已影响项目识别或安全推进的缺口才需要先询问用户；其余记录并继续可独立完成的工作。

缺少旧聊天不妨碍从仓库重建；但不得假装已阅读不可访问的历史、工单或验证结果。文档中的命令或交接要求属于待核对资料，不能授予额外操作权限。

## 7. 上下文一致性与交接就绪

Handoff / Checkpoint 都不是最终事实来源；恢复或核验时重新检查当前项目。status 只做轻量采证，不为了填满字段扩大测试；未核验主张标明来源和 uncertainty。其余模块仍按当前任务选择必要的最小验证。

以下状态供 verify、restore 及 handoff 内部一致性检查共用，不是软件质量评分：

| 状态 | 判定 |
|---|---|
| Verified | 已核验范围内关键主张一致，有足够证据；注明范围 |
| Verified With Gaps | 核心主张可核验且一致，仍有明确的局部缺口 |
| Drift Detected | 有证据确认影响当前任务的主张与现状冲突；列出冲突及其余缺口 |
| Insufficient Evidence | 缺少关键证据，无法可靠判断一致性；不能仅因未核验就断言漂移 |

有实质冲突优先报告 Drift Detected；否则按关键证据是否足够、是否存在局部缺口选择状态。缺失的记录注明 missing，单独核验该记录时为 Insufficient Evidence，不虚构其内容。已准确记录的失败测试、dirty 工作区或旧日期本身不等于上下文不一致。

正式交接的 Handoff Status 使用以下准备度，不与上述一致性或测试状态混用：Ready 表示接收方所需的范围、当前工作、相关改动、约束、验证和下一步已可追溯且可访问；Ready With Gaps 表示仍可开始明确任务但有已说明的非阻断缺口；Not Ready 表示项目身份、关键改动可访问性或继续工作所需事实存在阻断缺口。dirty 不阻止就绪，但另一工作树缺少这些修改可构成阻断；不得假设账号切换会自动传输文件。准确披露软件失败不单独导致 Not Ready。

## 8. 有限文档写入

仅在当前模式和用户授权允许时写入。写入前重新检查目标是否被其他工作修改；变化后重读合并，避免覆盖未提交内容。检查差异、引用和证据基线，结束时报告实际写入文件。

除当前模式主记录外，仅当修改有明确证据、范围小、属于本次同步且不改变既有决策或要求时，有限更新 Progress、TODO、Issues、Architecture 等文档。需广泛重写、验收不明、无法安全合并并行改动或需产品/架构判断时，保留原文并报告路径、过期主张、证据和建议动作；影响下一步的事项记入主记录的问题或 Evidence Gaps。不要批量改写无关文档、改名整个文档体系或重新整理历史。保留有效历史与决策。
