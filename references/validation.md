# Skill 验证与维护

仅用于创建、修改或评估本 Skill，不是用户运行模块，不自动在真实用户项目上自测。默认使用简化版 **3+1 验收**，不因小修改重跑所有历史边界。

## 1. 基础结构检查

- 使用当前环境 skill-creator 的 `scripts/quick_validate.py` 校验入口与 frontmatter，记录实际结果；格式通过不代表行为通过。
- 检查必要 references/assets 引用、六个模块入口、openai.yaml 名称和默认只读 status、`allow_implicit_invocation: true`。
- 六模块共用 state-reconstruction.md；无明显规则冲突、失效引用、缺失文件或脚手架占位。模板填写说明可保留。
- 检查包中不含具体项目记忆、实际用户路径、账号信息、token、秘密或运行样例；不引入运行脚本及固定项目依赖。

通过即可，不建立额外复杂矩阵。

## 2. 一次核心主流程

只建立一个最小隔离项目：开发进行中 → checkpoint → handoff → 独立 Codex 接收 → restore。

验证断点准确记录 WIP、部分实现和下一步，不将未完成工作标为 Completed；交接保留任务、关键状态、Git 基线、未完成工作、约束与下一步；没有旧聊天的接收方仅凭 Skill、项目、Handoff/Checkpoint 恢复关键状态，给出明确可执行的下一步。

独立执行者接收真实请求和最小原始资料，不接收预期答案或前次结论。用实际文档、执行结果和前后文件/Git状态确认结果与只读边界；证据保持简洁并保存在 Skill 包外。不使用真实项目、不调用外部服务。核心链路成功即 PASS，未执行不能用静态检查代替。

## 3. 一次冲突测试

在同一隔离样例中制造一个明确冲突，例如记录声称某功能完成而代码仍未完成。运行 restore 或 verify；能依据共享规则重新核对代码/Git，发现并明确报告不一致或证据缺口、不盲信记录即 PASS。

## +1. 只按修改范围追加

默认不运行其他历史边界测试。改 Git 状态判断则补相关 working-tree 场景；改公共重建规则则补证据冲突；改 decision/ADR 则补决策场景；改 restore 则针对改动核验恢复行为。上述核心主流程或冲突测试已覆盖的部分直接复用，不重复运行。仅模板、README 或不影响行为的文字变化不要求完整回归。

失败时先修复 Skill，再重跑失败及直接受影响场景，不降低证据标准或安全边界，不重跑已通过且未受影响的测试。

## 简洁报告

仅列：基础结构 PASS/FAIL；核心主流程 PASS/FAIL；冲突测试 PASS/FAIL；额外测试及结果（或无）；未覆盖的重要风险；本次核心验收是否通过。无法执行项明确说明，不冒充 PASS。不要生成冗长重复证据或不必要的测试矩阵。

## Full Regression / 可选扩展回归

保留以下历史场景作为参考，默认不执行。仅在大版本升级、公共状态重建规则重大修改、难以定位的可靠性问题或用户明确要求发布级完整验收时考虑选择；不是自动触发，更不覆盖用户指定的简化验收范围。

| 场景 | 可观察的通过条件 |
|---|---|
| 自定义中文/英文文档与合并状态页 | 复用原文档，不机械创建整套文件 |
| 聊天声称完成，实际仅占位/未接线 | 不误报完成，定位实现缺口 |
| Handoff 属于另一分支/工作树 | 核查当前范围和差异，不照搬未提交成果 |
| HEAD 相同但已修改当前任务代码 | 识别相关变化，重新判断旧验证是否适用 |
| 只有无关文件变化或日期较旧 | 不无依据宣布整个 Handoff 失效 |
| 代码违背 Accepted ADR | 记录偏差，保留决策与理由 |
| 测试失败、被阻碍或超时 | 如实分类，不声称成功；不越界修代码 |
| 无 Git、无 Handoff 或来源不可访问 | 有限恢复并说明缺口，不编造历史 |
| 多项目候选不明、大型多模块项目 | 不猜项目；确定后仅检查所需模块及依赖 |
| 连续 compress，含长约束和未提交历史 | 无流水账累积，关键约束/风险/证据不因行数删除，重要历史可找回 |
| compress 发现大量文档过期 | 重点维护 Handoff，只有明确小范围同步才改其他文档 |
| status、restore 或 verify 单独调用 | 报告完整，项目文件不被改写 |
| 已知失败但交接完整；或关键事实未检查 | 分别区分软件质量与上下文质量；未核验不能报 Verified |
| 压缩中目标文档出现并行修改 | 重读合并，不覆盖并行内容 |

其他按需场景：无模式调用只读 status；compress 不生成账号交接声明；dirty 工作区仍可准确交接；health-check 路由 verify；明确“检查后同步”才进入适当写入流程。公共事实标准与项目记忆隔离先由基础检查核对，不为覆盖清单反复执行同一链路。
